# Cryptographic Protocol — ZeroTrace Messenger v0.1.0-experimental

This document is the authoritative description of what the code actually
does. Where the implementation deviates from the Signal protocols it is
based on, the deviation is stated here, not hidden. Nothing in this document
claims an independent review — there has been none.

## 1. Primitives

| Purpose | Primitive | Implementation |
|---|---|---|
| Classical key agreement | X25519 | `x25519-dalek` 2 |
| Post-quantum KEM | ML-KEM-1024 (FIPS 203) | `ml-kem` 0.2 |
| Classical signatures | Ed25519 | `ed25519-dalek` 2 |
| Post-quantum signatures | ML-DSA-87 (FIPS 204) | `ml-dsa` 0.1 |
| Message AEAD | ChaCha20-Poly1305 | `chacha20poly1305` 0.10 |
| KDF / MAC | HKDF-SHA-256, HMAC-SHA-256 | `hkdf`, `hmac` (RustCrypto) |
| Hash | SHA-256 | `sha2` |

**Deviation, stated plainly:** the original brief specified AES-CBC+HMAC for
message encryption. The implementation uses ChaCha20-Poly1305 (a reviewed
AEAD) instead — a deliberate, documented change, not an oversight.

**Forbidden crates:** `pqc_kyber` / `pqcrypto` are never used (pre-standard
Kyber, KyberSlash RUSTSEC-2023-0079). Only FIPS 203 ML-KEM and FIPS 204
ML-DSA are used.

**Audit status:** `ml-kem` and `ml-dsa` are unaudited at the versions used.
See `docs/DEPENDENCIES.md`.

## 2. Identity

Each device generates, in the Rust core:

- Ed25519 identity key pair (`ik_ed`)
- X25519 identity key pair (`ik_x`)
- ML-DSA-87 signing key pair (`ik_pq`) — the secret is stored as a **32-byte
  seed** (`SigningKey::from_seed`); no 4032-byte expanded key is stored.
- ML-KEM-1024 encapsulation key pair (`ek_pq`) — the signed prekey.
- X25519 signed prekey (`spk_x`), signed with Ed25519.

Identity bundle wire format v1 (fixed offsets, `BUNDLE_LEN = 7553` bytes;
public part `PUBLIC_LEN = 4258`):

```
ed_pk 32 | x_pk 32 | mldsa_pk 2592 | mlkem_ek 1568 | spk_x 32 | signatures...
```

**Fingerprint** (must match in Rust and Kotlin, and is what users compare):

```
SHA-256( ed_pk || SHA256(mldsa_pk) || SHA256(mlkem_ek) || onion_utf8 )
first 24 bytes, rendered as 12 groups of 4 lowercase hex chars
```

The onion address is **not** identity proof. App identity (these keys) and
Tor identity (the onion service key, generated by Arti and stored in the
Arti state directory) are separate. An unexpected identity change for a
known contact is never silently accepted — the contact store refuses to
overwrite a fingerprint without explicit re-verification.

## 3. QR pairing — the commitment

A QR code cannot hold post-quantum keys (ML-DSA-87 public key 2592 bytes,
signature 4627 bytes; QR capacity ~3 KB). So the QR carries a **commitment**,
not the keys:

```json
{
  "p": "zt", "v": 1,
  "onion": "<62-char .onion address>",
  "ik_ed": "<hex 32>", "ik_x": "<hex 32>", "spk_x": "<hex 32>",
  "pq_id_hash": "<hex SHA-256 of ML-DSA-87 pk>",
  "pq_ek_hash": "<hex SHA-256 of ML-KEM-1024 ek>",
  "sig_ed": "<hex Ed25519 signature over the canonical serialisation>",
  "exp": "<unix expiry, 600 s>",
  "nonce": "<hex 16>",
  "caps": ["pqxdh-sync-v1", "dr-chacha-v1"]
}
```

~700 bytes. The full PQ keys are exchanged afterwards over the Tor channel
and verified against these hashes by `nativeVerifyBundle`. A peer presenting
different PQ keys than the QR committed to is rejected.

QR parsing is strict: unknown protocol/version, bad hex lengths, expired or
far-future expiry, bad onion format, missing capability → rejected. A
fuzzing harness for the parser is planned, not yet written.

## 4. PQXDH-Sync v1 — the handshake

**Status: EXPERIMENTAL. New construction, no independent review. Do not
describe it as "Signal PQXDH" without the "-Sync v1" qualifier and the
experimental label.**

PQXDH-Sync v1 is a serverless adaptation of Signal PQXDH rev 3:

| Signal PQXDH (server) | PQXDH-Sync v1 (this app) |
|---|---|
| Initiator fetches a prekey bundle from a server | Initiator requests the bundle live, over the onion channel, from the peer |
| One-time prekey (optional) | **No one-time prekey** — there is no server to hold one |
| Asynchronous | **Synchronous round trip** — both peers must be online |
| Info strings `Signal_PQXDH...` | Info strings `ZeroTrace-...` |

Message flow:

```
Initiator (A)                          Responder (B)
   | -- full bundle (B frame) ----------> |  verify vs QR commitment
   | <-- full bundle (B frame) ---------- |  verify vs QR commitment
   | -- Init (I frame) -----------------> |  verify, respond
   | <-- Response (R frame) ------------- |
   |  both derive the same ratchet state  |
```

- **Init**: `[0]=0x01, [1..33]=ephemeral X25519 pk, [33..1601]=ML-KEM-1024
  ciphertext, [1601..1601+4258]=initiator public identity`.
- **Response**: responder's ML-KEM encapsulation + confirmation, verified by
  the initiator before the session is marked ready.
- Domain separation: every HKDF call uses a distinct `ZeroTrace-...` info
  string; handshake version is validated; replayed or downgraded handshakes
  are rejected (a second Init for an already-established session is dropped).
- Fresh secrets: ephemeral X25519 keys and KEM encapsulations are generated
  per handshake; nothing is reused across sessions.

**Known gap:** there is no one-time prekey, so a compromised signed prekey
has more value to an attacker than in Signal's design. This is inherent to
the serverless design and is mitigated only by the per-handshake fresh
ephemeral + KEM. It is not hidden and not solved.

## 5. Double Ratchet + DH+KEM

After the handshake, messaging uses the Signal Double Ratchet rev 4, with
one addition at every DH step: a **fresh ML-KEM-1024 encapsulation** is
folded into the root KDF alongside the DH output. So each ratchet step
derives keys from `DH(X25519) || KEM(ML-KEM-1024)`. The chain KEM
ciphertext is repeated in every message header so that an out-of-order
first-seen message can still establish its chain (~1.6 KB/message overhead,
documented, not hidden).

- Message keys are never reused; nonces are never reused (ChaCha20-Poly1305
  with a per-message key/nonce derived from the chain).
- Out-of-order messages: supported up to `MAX_SKIP = 1000` skipped keys per
  chain; `MAX_SKIPPED_KEYS = 1000` total stored skipped keys.
- Duplicate / replayed messages: rejected (a message key is consumed on
  first successful decrypt).
- Invalid ciphertext / bad authentication tag: the message is dropped and
  **chain state is not consumed** — a failed decrypt must not advance the
  ratchet (this was a real bug found by the test suite and fixed; see
  `DEVELOPMENT_STATUS.md`).
- A failed decrypt never crashes the session and never logs content.

**What is NOT implemented:** ML-KEM Braid / SPQR-style incremental KEM
ratcheting. That needs incremental ML-KEM plus erasure coding, which does
not exist in the crates used. The DH+KEM step above is the implemented
mechanism; do not describe the app as having Braid/SPQR.

## 6. Wire framing (onion streams)

Every onion stream carries frames: `[type:1][len:4 big-endian][payload]`.

| Type | Meaning |
|---|---|
| `B` (0x42) | Full identity bundle (JSON) |
| `I` (0x49) | Handshake Init |
| `R` (0x52) | Handshake Response |
| `M` (0x4D) | Ratchet (chat) message |

Frames larger than 1 MB are dropped and the stream is closed.

## 7. FFI boundary (Kotlin ↔ Rust)

- Session handles are opaque `u64` ids. Private keys **never** cross into
  Kotlin, with exactly two documented exceptions: the identity bundle
  crosses **out** once (generate → Keystore wrap) and **in** once (unwrap →
  session open). Both crossings are documented; the Kotlin caller zeroes
  the byte array after use where possible.
- Plaintext crosses only as the active session's message bytes, in
  short-lived arrays that are zeroed after encryption.
- Every JNI error is reported to Java as a `RuntimeException`; a Rust panic
  never crosses the boundary (a panic would abort the process — the code is
  written to return `Result` everywhere instead).
- Unavoidable copies: the identity bundle exists in Kotlin memory briefly
  during wrap/unwrap; the plaintext message exists briefly during
  encrypt/decrypt. This is inherent to the JNI design and is stated here
  rather than claimed away.

## 8. Session destruction

`lockAndDisconnect()`: stops the receive/timeout/accept loops, closes the
Rust session (handle invalidated, ratchet state zeroed), stops the Tor
client, clears the message list, zeroes the in-memory identity copy. The
wrapped identity on disk is retained so the user can start again without
re-creating it — it can only be unwrapped by the Keystore key.

What is **not** claimed: guaranteed erasure from NAND flash (impossible to
guarantee on Android), protection against a live forensic dump of RAM, or
any USB-triggered wiping / decoy-chat / anti-debugging behaviour. None of
those are implemented, per the brief.
